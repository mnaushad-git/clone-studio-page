# Odoo Product Variant Model — Reference

How Odoo's native variant system works, and how this repo maps onto it in **both**
directions: the **push** importer (`app/services/catalogue/odoo_import_planning.py`'s
`plan_attributes`/`plan_variants`, `app/services/catalogue/odoo_import_service.py`'s
`_apply_attribute_item`/`_apply_variant_item` — Postgres/JSON catalogue → Odoo), and
the **pull** sync (`app/services/catalogue/odoo_catalogue_sync_service.py`'s
`sync_variants`/`_resolve_variant_attributes`/`_attribute_code_for` — Odoo → Postgres,
§"Pull direction" below). Read this before touching either — getting the layer
boundaries wrong is the single biggest source of bugs here.

## The four-layer graph

```
product.attribute                         "Box Size"                (shared, global-ish
  └─ product.attribute.value              "Small Box (8pcs)"          master data —
                                           "Large Box (16pcs)"         reused across
                                                                       every product that
                                                                       has this axis)

product.template ("Berry Truffle")
  └─ product.template.attribute.line       joins template ↔ attribute — WHICH values
       attribute_id = "Box Size"           apply to THIS template, and the
       value_ids = [Small, Large]          create_variant mode ("always"/"dynamic"/
                                            "no_variant")

  Odoo auto-computes, per template.attribute.line combination across ALL of a
  template's attribute lines:
  └─ product.template.attribute.value      the per-template-per-value join row —
       (one per template × attribute-value    this is what carries price_extra,
        pair actually in use)                 NOT product.attribute.value itself.
                                               Also the row read back to identify
                                               which combination a product.product is.

  └─ product.product                      auto-generated, one per combination. A
       (auto-generated by Odoo)             template with 2 attribute lines (Box Size ×
                                            Flavor), each "always create variant", gets
                                            the full Cartesian product — 2 sizes × 2
                                            flavors = 4 product.product records. Odoo
                                            creates/deletes these itself as attribute
                                            lines change; this importer never calls
                                            product.product.create directly.
```

## Key facts that drive every design decision here

1. **Attributes and their values are shared master data.** "Flavor" with values
   "Milk"/"Dark" should exist *once* in Odoo, reused by every template that has a
   flavor axis — not recreated per product. This is structurally different from
   categories/templates (1:1 with a canonical external key) and is why variant
   planning needs its own matching pass (`plan_attributes`), separate from
   `plan_products`, run once per import rather than once per product.

2. **You never create `product.product` directly for combination variants.** You
   create/update the `product.template.attribute.line` (attribute_id + value_ids on
   the template); Odoo's ORM computes/creates/removes the `product.product` rows as a
   side effect of that write. This mirrors the pre-existing absence of
   `("product.product", "create")` in `write_client.py`'s allowlist for the single
   default variant — the same absence-of-create pattern extends to combination
   variants.

3. **Read-back is via the template, not a create() return value.** After
   creating/updating `product.template.attribute.line` records, find the resulting
   `product.product` by `search_read("product.product", [["product_tmpl_id","=",
   tmpl_id]], ["id","product_template_attribute_value_ids"])`, then for each returned
   variant `read("product.template.attribute.value", ptav_ids,
   ["product_attribute_value_id"])` and compare the set of underlying
   `product.attribute.value` ids against the specific combination you're looking for —
   the variant whose combination-set matches exactly is the one you want.
   (`OdooCatalogueImportService._find_matching_variant` implements exactly this.)

4. **`price_extra` lives on `product.template.attribute.value`, not on
   `product.attribute.value`.** It's a per-template override (e.g. "Large Box costs
   +8 SAR *on this template*"). This importer deliberately does **not** write it —
   Postgres's `catalogue_product_prices` (absolute amount, deltas already composed) is
   the source of truth for what the storefront charges, and `order_push.py` already
   sends an explicit `price_unit` per sale-order line, so Odoo's own `price_extra`
   computation is never consulted by the order path. Setting it would be write effort
   with no functional consumer and a second number that can drift from the first.

5. **`create_variant` mode matters, and must always be `"always"`.**
   - `"always"` (this app's only supported mode) — every combination gets a real,
     stocked, sellable `product.product` immediately.
   - `"dynamic"` — variants materialize lazily on first sale-order/quotation line.
   - `"no_variant"` — no per-combination `product.product` is ever created; the
     attribute becomes a pure "note" on the order line with no separate SKU/stock.

   Terrific Bites already has per-variant SKU/price/availability rows in Postgres
   (`catalogue_product_variants`), so `"always"` is the only mode consistent with that
   model. `plan_attributes()` explicitly verifies a matched existing attribute's
   `create_variant == "always"` and `BLOCKED`s
   (`EXISTING_ATTRIBUTE_WRONG_CREATE_VARIANT_MODE`) rather than silently reinterpreting
   an installation's existing choice.

## Postgres-side identity: `catalogue_product_attribute_values`

This table is the single source of truth for a variant's per-axis attribute data —
there is no separate `variant_attributes` JSONB representation on
`catalogue_product_variants` (an earlier revision of this feature had one; it was
retired during the "Generic N-Attribute Pipeline" rollout specifically because a second
representation could silently drift out of sync with this one, as it briefly did).
Every consumer — the storefront catalogue API, checkout pricing/variant-matching,
order snapshots, and admin/tracking display — reads this table directly.

```
catalogue_product_attribute_values
  variant_id                 FK -> catalogue_product_variants.id
  attribute_code              "size" | "flavor" — stable, app-internal axis key,
                               independent of display-label wording
  attribute_name_en            canonical Odoo product.attribute.name, e.g. "Box Size"
  value_label_en                canonical Odoo product.attribute.value.name
  odoo_attribute_id            adopted after match/create — never invented
  odoo_attribute_value_id      adopted after match/create — never invented
  UNIQUE (variant_id, attribute_code)
```

One row per (variant, axis) — a variant with 2 axes (size, flavor) gets 2 rows here.

## Write allowlist (`write_client.py`)

```python
("product.attribute", "create"),
("product.attribute.value", "create"),
("product.template.attribute.line", "create"),
("product.template.attribute.line", "write"),   # ADD a value to an existing axis
("product.template.attribute.value", "write"),  # price_extra (unused today, see #4)
```

Deliberately **not** allowlisted: `unlink`/`action_archive` on any of these models, or
`product.template.attribute.value.create` (Odoo creates these itself). Shrinking a
`value_ids` set can make Odoo delete a `product.product` that already has stock
moves/sale-order lines — retiring a combination is always a `BLOCKED` plan item
requiring a human to act in Odoo directly, never an automated write.

## Rollout safety: the shared-attribute duplication risk

The highest-consequence new failure mode this feature introduces: attributes are N:1
(many products share "Flavor"), unlike categories/templates which are 1:1 with a
canonical key.

- `plan_attributes()` re-runs its live exact-name match on every single `--plan`/
  `--dry-run`/`--apply` invocation — never cached across separate CLI invocations. A
  second `--apply` for a second product batch must rediscover the already-created
  "Flavor" attribute by name, not attempt to recreate it.
- Concurrent `--apply` runs are not safe for attribute-creating runs (the same
  implicit assumption today's category/template creates already rely on).
- `--reconcile` includes a duplicate-attribute-name detection check as a safety net
  catching this failure mode after the fact, even if a race somehow bypasses the
  plan-time gate.
- Gated by its own approval decision (`D20` in
  `data/catalogue/catalogue-business-approvals.json`), independent of the
  `D03/D04/D08/D10/D19` gate that covers category/template creation — see
  [odoo-catalogue-import.md](odoo-catalogue-import.md)'s Status section.

## Pull direction: ops creates a product/variant structure directly in Odoo

`OdooCatalogueSyncService.sync_variants()` (in `odoo_catalogue_sync_service.py`) is the
reverse of everything above — it *reads* the same four-layer graph instead of writing
it, so a product an ops team member creates directly in Odoo (with its own attribute
lines, values, and per-combination pricing) flows into Postgres automatically. This
already ran on a schedule before this feature (Celery Beat, every
`odoo_catalogue_sync_interval_seconds`, default 300s) — extending it needed no new
schedule, trigger, or approval gate: reading data from Odoo carries none of the
push side's duplication risk, since nothing is ever created in Odoo by this path.

**What already worked before this feature**: `_match_and_upsert_category`/
`_match_and_upsert_product`/`_match_and_upsert_variant` already create brand-new
Postgres rows for Odoo records with no Postgres presence — a wholly new Odoo product
already flowed into `catalogue_products`/`catalogue_product_variants` (one variant row
per Odoo `product.product`, i.e. per combination, since Odoo auto-generates one). **The
gap this closes**: nothing read *which* attribute combination each variant represents,
so every combination landed with `variant_attributes = null`/no
`catalogue_product_attribute_values` rows (indistinguishable, unlabeled variants), and
every variant of a template got the same flat `list_price` (no per-combination
`price_extra`).

### Combination resolution

1. `product_template_attribute_value_ids` is now requested on every `product.product`
   sweep (`VARIANT_SYNC_FIELDS`, `app/integrations/odoo/repositories/products.py`) — no
   extra Odoo round-trip, just one more field on the existing read.
2. Before the per-variant upsert loop, `sync_variants` collects every referenced
   `product.template.attribute.value` id across *all* variants swept this run and does
   exactly **2** bulk `read()` calls total (`OdooAttributeRepository.
   read_template_attribute_values`/`read_attribute_values`) — never one per variant.
   A failure here degrades gracefully (logged, no attribute labels resolved this run)
   rather than failing the whole variant phase.
3. `_resolve_variant_attributes(record, ...)` walks a variant's ptav ids through the
   two lookup dicts to produce the full per-axis `(attribute, value, price_extra)` list
   plus the combination's summed `price_extra`.

### `attribute_code` resolution ladder (`_attribute_code_for`)

Since `catalogue_product_attribute_values.attribute_code` is the stable key the
storefront's two fixed selector slots key off (`"size"` → the size picker, `"flavor"`
→ the flavor picker — see `product.$id.tsx`), an Odoo-originated attribute needs to be
mapped onto one of those two codes to render at all. Three tiers, checked in order:

1. **Reuse** — `ProductAttributeValueRepository.get_by_odoo_attribute_id()`: if this
   exact Odoo attribute id was already recorded (a prior pull-sync run, or the push
   side having created it), reuse its code verbatim. This is checked *before* the name
   heuristic and always wins — the same Odoo attribute must always map to the same
   code everywhere, regardless of which product references it or what its name looks
   like.
2. **Name heuristic** (`_SIZE_ATTRIBUTE_NAMES`/`_FLAVOR_ATTRIBUTE_NAMES` constants,
   lowercased match) — every axis name already in use in
   `data/catalogue/products.json` ("Pack Size", "Box Size", "Gift Tier", "Cake Size",
   "Ice Cream Size" → `"size"`; "Flavor"/"Flavour" → `"flavor"`). Lets an ops-defined
   attribute with a familiar name render correctly on its very first sync, with no
   prior Postgres row to reuse from.
3. **Positional fallback** for a genuinely unrecognized name: first unmatched axis on
   *this* variant → `"size"`, second → `"flavor"`, third and beyond → a slugified
   version of the attribute name (e.g. `"icing-type"`).

**Update**: the storefront selector (`src/routes/product.$id.tsx`) now renders any
number of axes generically — `catalogue_product_attribute_values` is the single source
of truth read by every consumer (storefront API, checkout pricing, order snapshots,
admin/tracking display), with no separate `variant_attributes` JSONB representation to
fall out of sync with it. A slugified tier-3 code still reaches the customer; it just
renders with the generic list style (like `"flavor"`) rather than `"size"`'s bordered-
box style, since it has no prior visual precedent. See
`docs/architecture/target-architecture.md` and the plan history for the "Generic
N-Attribute Pipeline" rollout that retired the old two-slot-only limitation described
in earlier drafts of this document.

### Pricing

`sync_prices` now computes `amount = template.list_price + price_extra_by_variant[id]`
— the summed `price_extra` from step 2 above. This is the mirror image of the push
side's decision *not* to write `price_extra` (§4 above): here, Odoo genuinely is the
authoritative source for ops-defined per-combination pricing (that's the whole point of
this feature — ops prices variants directly in Odoo), so reading it is the correct
direction for that same authority split, not a contradiction of the push side's
decision, which was about *writing* it from Postgres, a different direction with
Postgres as the authority.
