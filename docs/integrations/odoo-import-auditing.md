# Odoo Import Auditing

Describes the two PostgreSQL audit tables (Alembic migration `0003_odoo_import_runs`)
every import mode writes to (except `--validate`/`--reconcile`, which are read-only
and never write a run row).

## odoo_catalogue_import_runs

One row per `import_odoo_catalogue` invocation in `PLAN`/`DRY_RUN`/`APPLY` mode
(`app/models/integration/odoo_import_run.py`). Records: environment identity
(`environment_fingerprint`, `odoo_version`, `company_id`, `company_name`, `currency`),
the three idempotency checksums (`source_checksum`, `approval_checksum`,
`import_plan_checksum` — see [odoo-import-idempotency.md](odoo-import-idempotency.md)),
`mode` (`VALIDATE | PLAN | DRY_RUN | APPLY | ROLLBACK_PLAN`), `status` (`PENDING |
RUNNING | SUCCEEDED | FAILED | BLOCKED | PARTIALLY_COMPLETED | ROLLBACK_REQUIRED`),
planned vs. actual create/update/skip/(blocked|failed) counts, `correlation_id`,
`initiated_by`, and `error_summary`. Never deleted — an append-mostly audit log.

## odoo_catalogue_import_items

One row per category/product/variant/image/XML-ID a run considered
(`app/models/integration/odoo_import_item.py`), FK'd to its run. `entity_type`
(`CATEGORY | PRODUCT_TEMPLATE | PRODUCT_VARIANT | PRODUCT_IMAGE | EXTERNAL_XML_ID`),
`planned_action` vs. `actual_action` (`CREATE | UPDATE | MATCH | SKIP | BLOCKED`),
`odoo_record_id`, `external_xml_id`, `before_state_json` (for updates, so
[odoo-import-rollback.md](odoo-import-rollback.md) can propose restoration),
`proposed_values_json` / `written_values_json` (**never contains base64 image
payloads** — see [odoo-image-import.md](odoo-image-import.md)), `result_status`
(`PENDING | SUCCEEDED | FAILED | SKIPPED | BLOCKED | ROLLBACK_REQUIRED`),
`error_code`/`error_message`, `started_at`/`completed_at`.

Indexed on `import_run_id`, `canonical_external_key`, `canonical_sku`,
`odoo_record_id`, `external_xml_id`, `result_status` — every lookup the matching
logic, reconciliation, and rollback planner need is index-backed, not a table scan.

## Correlation and traceability

Every run gets a `correlation_id` (`import_{mode}_<12 hex chars>`, generated by the
CLI script) threaded through: every Odoo client/write-client call
(`OdooTransport`/`OdooWriteClient` structured logs), every `odoo_catalogue_import_items`
row, and the run row itself. Given a `correlation_id` or `import_run_id`, every Odoo
call and every PostgreSQL write that run made can be reconstructed from logs + the two
audit tables alone.

## What is never logged or persisted

- Odoo password/API key/session id — same redaction discipline as Phase 4
  (`OdooIntegrationError.safe_context()`); this phase introduces no new leak surface.
- Base64 image content — `written_values_json` for an image item stores
  `role`/`display_order`/`checksum`/`source_path` and the literal marker
  `"image_payload": "EXCLUDED_FROM_AUDIT_LOG"`, never the encoded bytes.
- Anything from a `--dry-run`'s simulated payloads that would require an actual Odoo
  read to produce (dry-run never calls Odoo beyond the read-only matching pass already
  needed for `--plan`).
