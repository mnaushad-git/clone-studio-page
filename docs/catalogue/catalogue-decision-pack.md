# Catalogue Decision Pack

Phase 2B deliverable — Catalogue Decision Resolution and Import Readiness. Resolves the 13
open decisions logged in [catalogue-decisions-required.md](catalogue-decisions-required.md)
(Phase 2A) against the 20 MVP-default instructions issued for this phase, plus 2 items
discovered while resolving them. The machine-readable version of everything below is
[data/catalogue/catalogue-decisions.json](../../data/catalogue/catalogue-decisions.json)
(`D01`–`D22`); this document is the narrative form for human review and sign-off.

**Scope discipline:** this phase produces decisions and readiness documentation only.
Nothing in this document (or its sibling files) imports anything into Odoo, creates
PostgreSQL tables/models, implements a FastAPI catalogue endpoint, or changes the
Storefront/Admin UI. See [catalogue-import-readiness.md](catalogue-import-readiness.md)
for what remains before those steps can start.

## D01 — Canonical product count: 26, not 28

1. **Issue:** Two other docs in this repo (`docs/current-state/mock-data.md`,
   `docs/architecture/implementation-roadmap.md`) state "28 products." Direct inspection of
   `src/lib/products.ts` confirms 26.
2. **Why it matters:** Every downstream estimate, test fixture, and import plan that cites
   "28" is quietly wrong.
3. **Options:** (a) treat 26 as ground truth, mark 28 obsolete; (b) treat 28 as ground truth
   and search for 2 missing products.
4. **Recommendation:** (a). No evidence of 2 removed products exists anywhere (git history,
   admin store, changelog).
5. **Consequences:** The other two docs still say "28" until someone edits them (out of
   this phase's scope to touch); anyone reading them should defer to this phase's audit.
6. **Classification:** Technical implementation decision.
7. **Blocks:** Nothing.
8. **MVP-safe default or needs approval:** Safe to accept as MVP default — `APPROVED`.

## D02 — Category structure: flat, 6 categories, no hierarchy

1. **Issue:** `categories.json` includes a `parent_external_key` field for
   forward-compatibility; it is `null` for all 6 today.
2. **Why it matters:** Determines whether Postgres/Odoo category modeling needs to support
   a tree (self-referencing FK, recursive queries) or a flat list.
3. **Options:** (a) keep flat; (b) introduce a hierarchy now.
4. **Recommendation:** (a). Nothing in the current UI/navigation/admin tooling implies or
   needs a hierarchy.
5. **Consequences:** Category schema can be a simple flat table for the MVP; the
   `parent_external_key` field stays available for later if a real need emerges.
6. **Classification:** Architecture decision.
7. **Blocks:** Nothing.
8. **MVP-safe default or needs approval:** Safe to accept as MVP default — `APPROVED`.

## D03 — Category codes: keep CUP / CAK / CHO / DON / GIF / EXT

1. **Issue:** Category codes were generated by Phase 2A, not business-assigned. They are
   the SKU prefix for every one of the 26 products — changing a code cascades into every
   SKU in that category.
2. **Why it matters:** Codes become permanent the moment SKUs are imported into Odoo.
3. **Options:** (a) keep the existing 3-letter codes as-is; (b) expand to clearer 4-5
   letter codes (`CAKE`/`CHOC`/`DONUT`/`GIFT`/`EXTRA`); (c) ask the business for entirely
   new codes.
4. **Recommendation:** (a) keep as-is. See
   [category-approval-register.md](category-approval-register.md) for the full rationale,
   including the noted (but not acted on) legibility concern that `GIF` reads identically
   to the image-format acronym and `CAK`/`CHO`/`DON` are truncations.
5. **Consequences:** If accepted, these 6 codes are final SKU prefixes going forward. If
   the business instead wants option (b), all 26 SKUs must be regenerated together before
   Odoo import (cheap now, since nothing is imported yet).
6. **Classification:** Business decision.
7. **Blocks:** Odoo import (cascades into every SKU).
8. **MVP-safe default or needs approval:** Requires explicit business confirmation —
   `BUSINESS_CONFIRMATION_REQUIRED`.

## D04 — Product SKU convention and sequence

1. **Issue:** All 26 SKUs are generated (`TB-<CODE>-<3-digit-sequence>`), not
   business-assigned. Sequence = the product's array position within its category in
   `src/lib/products.ts`.
2. **Why it matters:** SKUs become the Odoo `default_code` — the primary human-facing
   product reference in ERP, invoices, and (eventually) customer-facing order confirmations.
3. **Options:** (a) accept convention + current sequence; (b) re-sequence by another rule
   (price, alphabetical, launch date); (c) change the convention itself.
4. **Recommendation:** (a). See
   [sku-approval-register.md](sku-approval-register.md) for the full 26-row table and
   rationale for not inventing an alternative ordering principle.
5. **Consequences:** Sequence numbers carry no business meaning (e.g. `buttercream-cake` is
   `TB-CAK-001` simply because it's the only cake, not because it's the flagship product).
   This is fine for an MVP SKU but should not be read as a ranking by anyone downstream.
6. **Classification:** Business decision.
7. **Blocks:** Odoo import.
8. **MVP-safe default or needs approval:** Requires explicit business confirmation —
   `BUSINESS_CONFIRMATION_REQUIRED`.

## D05 — External key convention

1. **Issue:** Need a stable, cross-system identifier namespace, separate from the SKU.
2. **Why it matters:** Used as the idempotency key for Odoo `ir.model.data` external-id

   repeated sync runs safe.
3. **Options:** (a) `terrific_bites.product.<slug>` / `terrific_bites.category.<slug>` (the
   convention already generated); (b) a different namespace.
4. **Recommendation:** (a) — already applied consistently, purely technical, no commercial
   content.
5. **Consequences:** Treated as permanent after import per this phase's own instruction.
6. **Classification:** Technical implementation decision.
7. **Blocks:** Nothing.
8. **MVP-safe default or needs approval:** Safe to accept as MVP default — `APPROVED`.

## D06 — Product and category slugs

## D07 — Currency

1. **Issue:** Confirm single-currency catalogue, no conversion applied.
2. **Why it matters:** Odoo's `list_price` is tied to a company/pricelist currency setting,
   not stored per-product — a mixed-currency catalogue would need per-product pricelists.
3. **Options:** (a) confirm SAR-only, no conversion; (b) investigate further.
4. **Recommendation:** (a) — confirmed by direct inspection, every product's `currency`
   field and every rendered price string is `SAR`.
5. **Consequences:** None for the catalogue itself. The target Odoo instance's company
   currency must separately be verified as SAR before import (see
   [odoo-configuration-checklist.md](odoo-configuration-checklist.md)).
6. **Classification:** Technical implementation decision.
7. **Blocks:** Nothing for the catalogue; the company-currency check blocks Odoo import.
8. **MVP-safe default or needs approval:** Safe to accept as MVP default — `APPROVED`
   (with a separate `ODOO_VERIFICATION_REQUIRED` note for the instance-side currency check).

## D08 — Tax / VAT mapping and price tax-treatment

1. **Issue:** No per-product or per-category tax class exists — only one site-wide 5% VAT
   rate applied at checkout. Separately, and more concretely: **the PDP tells the customer
   prices already include VAT, while the checkout code adds VAT on top of the same price.**
2. **Why it matters:** Odoo needs a real `account.tax` mapped to every product template.
   The inclusive/exclusive question determines whether prices need to change at all when
   the real checkout is built, or whether the current checkout math is simply wrong today.
3. **Options:** (a) introduce a logical placeholder tax reference now, resolve the real
   Odoo tax id later; (b) leave `tax_reference` null until an Odoo instance exists; (c)
   model per-category tax classes (e.g. catering vs. retail).
4. **Recommendation:** (a) — use `STANDARD_SALES_VAT` as the logical label when
   `tax_reference` is eventually populated (no canonical file was changed to add this in
   this phase — see "Canonical seed file changes" below). No per-category tax class is
   justified; nothing in the 26-product catalogue suggests a second tax treatment.
5. **Consequences:** Checkout/pricing work cannot proceed correctly until the business
   states which of "prices include VAT" (PDP copy) or "VAT added at checkout" (cart math)
   is true — seeD21 below for the specifics of this contradiction. This does **not** block
   catalogue import; Odoo's `list_price` is stored as a number either way.
6. **Classification:** Odoo configuration decision (tax mapping) with an embedded business
   decision (inclusive/exclusive — tracked separately as `D21`).
7. **Blocks:** Odoo import (real tax id unresolved). Does not block Postgres schema or
   frontend integration.
8. **MVP-safe default or needs approval:** Requires explicit business confirmation
   (which treatment is correct) **and** Odoo environment verification (real tax record) —
   `BUSINESS_CONFIRMATION_REQUIRED`.

## D09 — Unit of measure

1. **Issue:** No UoM concept exists anywhere in the app; Odoo requires one per template.
2. **Why it matters:** Affects quantity display, potential future bulk/catering SKUs, and
   Odoo's stock/valuation calculations if the business later adopts Stockable tracking.
3. **Options:** (a) default "Unit"/"Each" for all 26; (b) model per-product/category UoM.
4. **Recommendation:** (a). No catering, bulk, or quantity-based product exists in the
   audited 26 — every product, including `buttercream-cake`'s size options, is a single
   sellable item, not a quantity/UoM difference.
5. **Consequences:** Simple, correct default; the exact Odoo `uom.uom` record id still
   needs environment verification (naming varies by Odoo localization/edition).
6. **Classification:** Odoo configuration decision.
7. **Blocks:** Odoo import.
8. **MVP-safe default or needs approval:** Recommended default is safe, but the concrete
   Odoo record needs environment access — `ODOO_VERIFICATION_REQUIRED`.

## D10 — Odoo product type classification (Stockable / Consumable / Service)

1. **Issue:** `products.json`'s existing `product_type` field ("simple"/"variant_parent")
   describes variant structure, not Odoo's own Stockable/Consumable/Service classification
   that every `product.template` needs.
2. **Why it matters:** Determines whether Odoo tracks on-hand quantity/valuation for these
   products at all.
3. **Options:** (a) Consumable for all 26; (b) Stockable for all 26; (c) Service for all 26.
4. **Recommendation:** (a) Consumable. These are physical goods (ruling out Service), but
   the app has zero inventory-tracking concept today (ruling out the extra complexity of
   Stockable for an MVP).
5. **Consequences:** No warehouse/valuation workflow is required at launch. Can be upgraded
   to Stockable later, per-product, without any SKU or external-key change.
6. **Classification:** Odoo configuration decision.
7. **Blocks:** Odoo import.
8. **MVP-safe default or needs approval:** This is an operational choice, not a pure
   technical default — `BUSINESS_CONFIRMATION_REQUIRED`.

## D11 — Product variants scope

1. **Issue:** Only `buttercream-cake` has genuine per-product variant data (`sizes`/
   `flavors` literal on the product object). Every other product's size/flavor picker is a
   category-level default computed client-side, not per-product data.
2. **Why it matters:** Determines whether Odoo needs 1 template + 25 single-variant
   products, or 26 templates each with real attribute-driven variants.
3. **Options:** (a) model variants only where genuine per-product data exists
   (`buttercream-cake` only); (b) promote category-level defaults into real variants for
   all 26.
4. **Recommendation:** (a). Promoting category defaults would fabricate per-product data
   that doesn't actually exist today.
5. **Consequences:** 25 products import as single-variant templates; `buttercream-cake`
   imports with a Size (6"/9") × Flavor (Vanilla/Chocolate) attribute line generating real
   variants. Whether each variant needs its own `default_code` is
   `ODOO_VERIFICATION_REQUIRED`.
6. **Classification:** Architecture decision.
7. **Blocks:** Nothing immediately (structural approach only); the variant-SKU nuance
   blocks the Odoo import step specifically for this one product.
8. **MVP-safe default or needs approval:** Safe to accept as MVP default — `APPROVED`.

## D17 — Admin `ProductOverride` field split

1. **Issue:** The current `ProductOverride` schema conflates Odoo-owned commercial fields
   (`priceOverride`, `stock`) with PostgreSQL/Admin-owned merchandising fields (`visible`,
   `featured`, `badge`, `nameOverride`, `descriptionOverride`) in one object.
2. **Why it matters:** Without the split, an Admin edit could accidentally (or by design)
   permanently diverge from Odoo's authoritative price/stock/tax — exactly the failure mode
   rule 9 and `data-ownership.md` exist to prevent.
3. **Options:** (a) split into `product` (Odoo-synced) vs. `product_merchandising`
   (Admin-owned) per `data-ownership.md`; (b) keep the conflated shape for MVP.
4. **Recommendation:** (a) — this is already the architecture's specified design; adopting
   it now avoids building the wrong shape and correcting it later.
5. **Consequences:** See [final-data-ownership.md](final-data-ownership.md) for the
   complete field-by-field split this resolves to.
6. **Classification:** Architecture decision.
7. **Blocks:** Nothing (this is a resolution, not an open question).
8. **MVP-safe default or needs approval:** Follows an already-approved architecture rule —
   `APPROVED`.

## D21 — [Newly discovered] Price VAT-inclusive vs. VAT-exclusive contradiction

1. **Issue:** `src/routes/product.$id.tsx` displays "All prices include VAT" under every
   product's price. But `src/lib/store.ts`'s `selectTax()`/`selectTotal()` computes tax as
   5% **added on top** of the cart subtotal, and `CartDrawer.tsx`, `delivery.tsx`,
   `payment.tsx`, and `customize.tsx` all display that computed tax as a separate line.
2. **Why it matters:** These two behaviors cannot both be true. If prices already include
   VAT, checkout is currently over-charging customers by double-counting it. If prices are
   VAT-exclusive, the PDP is displaying an incorrect disclaimer.
3. **Options:** (a) confirm prices are VAT-exclusive, correct the PDP copy later; (b)
   confirm prices are VAT-inclusive, fix the checkout math to back VAT out instead of
   adding it; (c) leave unresolved for now.
4. **Recommendation:** Flag as a blocking business confirmation for checkout/pricing
   design — **not** for catalogue import. `sales_price` in `products.json` is stored as a
   plain number regardless of which interpretation eventually wins.
5. **Consequences:** No catalogue value changes. Checkout/pricing implementation cannot
   safely proceed until this is resolved (whichever direction the business picks changes
   real money calculations).
6. **Classification:** Business decision.
7. **Blocks:** Nothing for catalogue readiness; blocks future checkout/pricing work.
8. **MVP-safe default or needs approval:** Requires explicit business confirmation —
   `BUSINESS_CONFIRMATION_REQUIRED`.

## Canonical seed file changes made in this phase

**None.** All six canonical seed files under `data/catalogue/` (`categories.json`,
`products.json`, `product-merchandising.json`, `moments.json`, `recipients.json`,
`product-recommendations.json`) are byte-for-byte unchanged from Phase 2A.

Every value in those files that Phase 2A flagged with `_generated`/`_requires_confirmation`
(SKUs, category codes, tax/UoM nulls) is exactly the kind of business-sensitive value this
phase's instructions say must stay `PROPOSED` rather than be silently marked `APPROVED` in
the seed data. None of the 22 decisions above produced a *new* deterministic technical
identifier that wasn't already present and correctly generated — `external_key` and `slug`
(the only two things that qualified as safe-to-finalize technical identifiers) were already
