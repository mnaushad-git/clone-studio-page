## Convention

```
TB-<CATEGORY-CODE>-<3-digit-sequence>
```

`<CATEGORY-CODE>` = the category's code from [category-approval-register.md](category-approval-register.md)
(unchanged from Phase 2A: `CUP`/`CAK`/`CHO`/`DON`/`GIF`/`EXT`).
`<3-digit-sequence>` = the product's 1-based position within its category, taken in the
order the products already appear in `src/lib/products.ts`. This has no other meaning
(not launch date, not price rank, not popularity) — see rationale below.

## Sequence rationale (why array order, not another rule)

The decisions-required document raised whether sequence should encode something
meaningful (e.g. `buttercream-cake`, the highest-value item, being `TB-CAK-001`
"regardless of catalogue order," or sequence encoding launch date). No launch-date, price
tier, or popularity data exists anywhere in the source app to derive an alternative
ordering from — inventing one would be fabricated business data. Recommendation: accept
array order (the only ordering that already exists) as the final sequence. If the business
wants a different order, this table can be regenerated before Odoo import at effectively
zero cost, since nothing has been imported anywhere yet.

## What happens after approval

Once approved, `products.json`'s `sku_requires_confirmation` flips to `false` and
`sku_generated` remains `true` for provenance (these values were generated by tooling, not
originally present in the app, even after being approved). SKUs then become the
`product.product.default_code` value used at Odoo import (Step B of
[catalogue-migration-plan.md](catalogue-migration-plan.md)) and are treated as permanent
thereafter.
