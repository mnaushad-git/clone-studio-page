# Catalogue Migration Runbook

Covers Alembic revision `0002_catalogue_foundation`
(`backend/app/db/alembic/versions/0002_catalogue_foundation.py`, `down_revision =
"0001"`) — the 16-table catalogue schema described in
[postgresql-catalogue-schema.md](postgresql-catalogue-schema.md).

## Apply

```bash
cd backend
alembic upgrade head
```

Requires `DATABASE_URL` to point at a reachable PostgreSQL database (via
`backend/.env`, an exported env var, or docker-compose's own environment — see
[environment-variables.md](environment-variables.md)). `env.py` reads the connection
string from `app.core.config.get_settings()`, never from a value in `alembic.ini`.

Via Docker Compose:

```bash
docker compose exec backend-api alembic upgrade head
```

## Roll back

```bash
alembic downgrade 0001   # drops every catalogue/storefront/integration table
```

`downgrade()` drops tables in exact reverse dependency order (seed runs → sync
checkpoints → recommendations → product-recipients → product-moments → recipients →
moments → section-products → sections → merchandising → images → availability →
prices → variants → products → categories). Verified by actually running upgrade →
downgrade → upgrade against a real local PostgreSQL 16 instance — see the Phase 3
completion report.

## What's in this migration

All 16 tables in one revision — categories, products, variants, prices, availability,
images, merchandising, storefront sections + their product assignments, moments,
recipients, their two product-mapping join tables, recommendations, sync checkpoints,
and seed-run history. Every `UNIQUE`/`CHECK`/`FOREIGN KEY`/index from the SQLAlchemy
models is expressed explicitly (this migration was hand-written against the model
definitions, then verified with `alembic upgrade head --sql` for an offline dry-run and
a real `alembic upgrade head` against local PostgreSQL — not generated by
`--autogenerate`, since no prior schema existed to diff against).

Two `postgresql_where` partial unique indexes are worth knowing about if you're editing
this migration by hand:

- `uq_catalogue_product_variants_one_default_per_product` — unique on `product_id`
  `WHERE is_default` (at most one default variant per product).
- `uq_catalogue_product_prices_one_active_per_variant_currency` — unique on
  `(product_variant_id, currency)` `WHERE active` (at most one active price per
  variant+currency).

Both are PostgreSQL-specific (`postgresql_where`) — this schema is not
SQLite-compatible by design, per [CLAUDE.md](../../CLAUDE.md): "No SQLite-only
workaround should define the production schema."

## Troubleshooting

- **`FATAL: password authentication failed`** — `DATABASE_URL`'s credentials don't
  match your local PostgreSQL instance. The committed defaults
  (`backend/.env.example`, `tests/conftest.py`) intentionally use the generic
  `postgres:postgres` docker-compose credentials, not your local install's real
  password — override via an untracked `backend/.env` or an exported env var.
- **Migration fails partway through `upgrade head`** — Alembic runs each revision in
  one transaction (`context.begin_transaction()` in `env.py`); a failure rolls back the
  whole revision, not just the failing statement. Fix the underlying issue and re-run
  `alembic upgrade head` — it resumes from the last successfully applied revision.
- **Seeding fails with a reference error before writing anything** — that's the seed
  service's own validation, not a migration problem; see
  [catalogue-seeding.md](catalogue-seeding.md).
